# Defects

## 1. T1 already emits an `eq` term the grammar cannot parse (MAJOR)

**Files:** `ExplicitLean/ExplicitRw/Tactic.lean:138-205` (grammar);
producer side `/Users/.../T1-trace-capture/test/SimpTrace/out/ite.json`.

The `eq` step in T1's own `ite.json` is

```json
{"kind":"eq","pos":[0,1],"lhs":"if True then 1 else 2","rhs":"1",
 "by":"rfl","source":"reduceIte"}
```

`lhs` is pretty-printed with `if ... then ... else` syntax, which the whitelist
does not admit.

**Input / observed:**

```
explicit_rw [eq (if True then 1 else 2 = 1) by rfl at []] then rfl
  error: unexpected token 'if'; expected explicitRwTerm
```

**Expected:** parses, since this is a string the recorder emits today.
**Command:** `lake env lean /private/tmp/t2r4/t1ite.lean`

A workaround exists — `ite True 1 2` parses and elaborates to the same term
(verified: the error message pretty-prints it back as `if True then 1 else 2`)
— but it means the generator **cannot pass a recorded `lhs`/`rhs` string
through**; it must re-render every simproc equation into the whitelist dialect.
That is a real constraint neither `RESULT.md` nor the spec records. Either admit
`if _ then _ else _` in the grammar, or state in `RESULT.md` (and raise to the
coordinator for the spec) that `lhs`/`rhs`/`to` are whitelist-dialect terms
rather than free pretty-printed output. `reduceIte` is a very common simproc, so
this is not a corner case.

I verified the other three T1-emitted `eq` terms (`2 + 3`, `5`, `2 + 2 = 4`,
`True`) do parse: `lake env lean /private/tmp/t2r4/t1eq2.lean` is silent.

## 2. `.field` on a parenthesized term is rejected, with a misleading error (MAJOR)

**File:** `ExplicitLean/ExplicitRw/Tactic.lean:147` — `explicitRwTermIdent` gets
projection suffixes only because Lean's `ident` token swallows `h.elim`. Nothing
in the grammar allows a projection *after a closing parenthesis*, so
`(f x).1`, `(f x).fst` and `(hp q).elim` are all unparseable.

This directly hits the spec's own `absurd:<hyp>` close form whenever the
contradiction is an application rather than a bare hypothesis:

**Input / observed:**

```lean
example (p : Prop) (hp : ¬p) (q : p) (a b : Nat) : a = b := by
  explicit_rw [] then exact (hp q).elim
-- error: invalid 'by' tactic, expected type has not been provided
```

**Expected:** either it parses, or it is refused with a message naming the
grammar. The observed message mentions a `by` tactic that does not appear
anywhere in the file — it is what Lean reports after the grammar stops at `(`
and the leftovers are reparsed. A trace author hits this and hunts for a
nonexistent `by`.
**Command:** `lake env lean /private/tmp/t2r4/absurd.lean`

`f.elim` (bare identifier) works: `lake env lean /private/tmp/t2r4/absurd2.lean`
is silent. So the close form is expressible only when the false hypothesis is
already a name. **Fix direction:** add `explicitRwTerm:max "." (ident <|> num)`
as a postfix production. That admits no new *shapes*, only projection on an
already-whitelisted operand, so it does not weaken the whitelist.

## 3. `Type` and `Prop` are not admitted anywhere (MINOR)

**On `⟨a, b⟩` (coordinator's question).** Rejected in all four slots, as intended.
My recommendation: **keep excluding it.** No T1 trace emits it; the spec's close
forms never need it; and admitting anonymous constructors admits elaborator-driven
structure synthesis, which is exactly the kind of shape the whitelist exists to
keep out. If pp output ever produces one, the generator should render the
explicit constructor application instead.

**The binder rows are the headline.** `∀ x : α, p x`, `∃ x, p x` and
`fun x => f x` are how Lean *pretty-prints*; the grammar accepts only the
parenthesized-and-typed forms. Any generator that pipes `to`/`lhs`/`rhs` through
verbatim will fail on ordinary output. This is not unsafe — a lambda without
`by` runs no tactic — so it is a sufficiency gap, not a safety one, but it is
the largest one.
