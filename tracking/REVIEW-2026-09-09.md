## What the work establishes

The active design records stock `simp` during translation and emits checked raw
expression DAGs, explicit transports and bounded environment actions. The
generated selector uses the boundary apply path, with guards against pending
typeclass synthesis. This is a credible way to remove simplifier search from
the replacement call. The older schema-27 `simp_engine_apply` implementation is
legacy and must not be mistaken for the active search-free boundary path.

The project has addressed original-call comments, nested occurrences, applied
recording, caught replay failures, helper declarations, state preservation,
independent declaration comparisons, immutable invocation evidence, translated
import isolation and cold serialized output checking. Those are meaningful
correctness advances. Successful isolated modules still use a different
acceptance boundary from a complete translated dependency tree.

The scope is executable source `simp` and `simp only`. It does not yet remove
all search from Mathlib: other tactics and their internal simplifier calls are
outside this first milestone.

## September 10 follow-up: memory cleanup versus larger hardware

The user merged the supervisor branch; campaign HEAD is now `ee30955`.
Read-only inspection identified a concrete remaining retention issue:
`authenticate_v10_manifest` calls `manual_overlay._load_overlay_projected`
without `module_records`. That selects the full manifest rather than just the
override modules. The returned long-lived `Overlay` stores every module's
source bytes and occurrence metadata; `dict(raw)` also retains nested manifest
objects. Consequently, clearing the supervisor's `manifest_value` cannot
release all that data. The database has 16 overrides in only 14 modules, while
the supervisor overlay loads all 8,264. The worker already supplies
`module_records` and uses the existing sparse path. Reusing that path in the
supervisor is the first recommended bounded fix, retaining the prior complete
manifest validation and checking identical overlay identities and report
acceptance. Actual resident-memory savings have not been measured.

A second candidate is duplicate parsing: `campaign_worker.run_worker` retains
its parsed manifest and calls `translation_index.import_manifest`, which reads
and parses the same 216,029,215-byte manifest again and builds validation
records. Sharing authenticated parsed inputs, or isolating the indexing phase
in a short-lived process, could reduce peak memory while retaining validation.
This is a separate change and requires measurement and corruption controls.

The full cached success report JSON totals only 7,781,155 characters across
529 rows, plus about 5 MB of implementation identity strings, so compacting
that cache is a lower priority. Historical measurements show roughly 2.7–2.8
GiB supervisor/worker-process RSS after the earlier cleanup; they do not
establish the peak footprint of a difficult Lean compilation. The host has
64 GiB physical RAM; the current guard saw about 7.25 GiB immediately free and
speculative memory. Inactive pages are deliberately excluded. These are
host-wide admission measurements, not a per-job requirement above 64 GiB.

Recommendation: time-box work to the sparse-overlay fix and a controlled
before/after measurement of Python and Lean process peaks. If local execution
still stalls, a dedicated larger Linux host is a reasonable next experiment.
AWS documents `r7i.4xlarge` as 16 vCPUs and 128 GiB RAM; that is an illustrative
initial size, not a measured requirement or a price recommendation. Begin with
one translation worker and establish throughput before increasing concurrency.
Linux runtime artifacts and their evidence identities must be generated and
checked on that platform. No cloud resources were provisioned, no runtime
changes were made, and no new large Lean batch was launched in this assessment.

### Measured manual-overlay size

The override JSON itself is only 10,542 bytes (16 overrides in 14 modules).
An isolated fresh-process measurement of the existing full and sparse loaders
used the same current manifest and override database, released other manifest
references, ran GC and the existing macOS allocator advisory, then measured
RSS and recursively counted reachable Python object bytes without double
counting shared objects. The measurement ran no Lean compiler and made no
production-state or implementation changes.

| Measurement | Full supervisor overlay | Sparse overlay |
| --- | ---: | ---: |
| Retained modules | 8,264 | 14 |
| Retained occurrences | 83,627 | 216 |
| Source bytes | 96,127,495 | 204,046 |
| Reachable Python object bytes | 503,596,861 | 1,269,090 |
| RSS increase over baseline after release | 601,227,264 | 15,532,032 |
| Initial load peak RSS | 1,523,892,224 | 1,524,252,672 |

Both loaders returned identical overlay identities. The measured steady-state
RSS difference is about 559 MiB (0.55 GiB). Initial parsing peaks remained
about 1.42 GiB in both processes because both measurements parsed the whole
manifest first. The retained-object sizes are about 480 MiB versus 1.21 MiB.
This supports a small cleanup, but does not support treating it as the complete
solution to host memory pressure or delaying larger-machine evaluation for a
substantial optimization project. Production RSS savings may differ because
other code also retains shared data.

Reproducible script, per-mode results and source hash are saved under
`.lake/overlay-size-review-0al5mxcz/`; `summary.json` records the input manifest
hash, current HEAD and measurement limitations. Each mode ran in a separate
Python process under a 2 GiB RSS / 50-second profiling bound; both completed.
