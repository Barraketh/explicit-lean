# Explicit Lean

Status: working draft.

## 1. Success criterion

A theorem transformation succeeds when all of the following are true:

1. The theorem statement has the same elaborated type as the original, up to
   binder and universe-parameter names.
2. The theorem body is replaced by a body containing only allowed constructs.
3. The resulting Lean source compiles.

"The same statement" means alpha-equivalence of the elaborated theorem types:
the universe parameters correspond in the same order, the term binders have the
same order, types, and binder kinds, and the result propositions are identical
after consistently renaming those parameters and binders.
The only permitted source-level edits to a statement are to give names to
binders or universe parameters that were anonymous, inaccessible, or inserted
from the surrounding section, and to materialize those names in the theorem
header when necessary. A transformation may not change binder order, binder
types, explicitness, instance-implicit status, or the result proposition.

The replacement body does not need to resemble the original body. Compilation
against an alpha-equivalent statement is the test that the replacement body
proves the same theorem.

The set of allowed constructs will be defined separately.

## 2. First experiment: elaborated Mathlib proofs

The first experiment will test whether elaborated proof terms can serve directly
as replacement theorem bodies.

Select a small set of representative Mathlib modules containing proofs that use
a meaningful range of Lean features, including:

- implicit and universe arguments;
- type-class inference;
- coercions and overloaded notation; and
- common tactics, especially `simp`.

For each selected theorem:

1. Elaborate the original module with its Mathlib toolchain.
2. Obtain the theorem's completed elaborated proof term.
3. Print that term as Lean source using only allowed constructs, making recorded
   elaboration choices explicit where necessary.
4. Replace only the original theorem body with the printed term.
5. Compile the rewritten module.

The original imports and declaration names remain unchanged. Statements remain
alpha-equivalent under the definition above, but previously anonymous binders
may be named so the rewritten body can refer to them. The rewritten body does
not retain tactic syntax or need to preserve the structure or readability of
the original proof.

This experiment comes before designing a general transformation pipeline. Its
purpose is to identify which expression forms occur in realistic elaborated
proofs, which of them can be printed directly, and where additional lowering is
actually required.

### Initial result

The first experiment used Mathlib and Lean 4.32.2. It rewrote four theorems in
three modules:

- `Nat.count_le_setENCard` from `Mathlib.SetTheory.Cardinal.NatCount`;
- `GenContFract.first_num_eq` from
  `Mathlib.Algebra.ContinuedFractions.Translations`;
- `DualNumber.commute_eps_left` from `Mathlib.Algebra.DualNumber`; and
- `DualNumber.range_lift` from `Mathlib.Algebra.DualNumber`.

These cover `simp`, `simp only`, `simp_rw`, `ext`, implicit arguments,
type-class arguments, coercions, overloaded operations, and universes.

All three copied modules compiled after replacing only those four theorem
bodies. The successful representation:

- contains proof terms rather than tactic scripts;
- uses fully qualified constants and exposes ordinary implicit arguments;
- disables notation in the generated bodies;
- inlines private helper theorems generated by tactics; and
- leaves anonymous universe and type-class arguments for Lean to infer using
  `_` placeholders.

The generated body sizes were 915, 1,915, 5,339, and 356,153 UTF-8 bytes. The
three rewritten modules compiled in approximately 3.4, 3.4, and 33.3 seconds on
the initial test machine, with heartbeat limits disabled for the stress case.

Two other representations were informative but insufficient:

- A compact body with most implicit arguments omitted compiled the first two
  examples, but one algebraic proof elaborated differently because an
  overloaded use of `congr` was no longer constrained enough.
- A completely explicit closed proof term compiled three examples, but the
  largest body grew to roughly 8.7 MB and still had not finished checking after
  five minutes while using roughly 3.8 GB of memory.

### Rerun with named binders

The success criterion now treats theorem statements as the same when their
elaborated types are alpha-equivalent, as defined in Section 1. The rerun
materialized the original theorem parameters in each header and assigned stable
names to anonymous instance binders. A separate check elaborated those headers
and compared them with the original Mathlib declarations after aligning
universe parameters. All four retained the same binder order, binder types,
binder kinds, and result proposition.

With those names available, the exporter printed every recorded instance
argument rather than replacing instance arguments with `_`. It continued to
omit universe arguments, which Lean reconstructs from the explicitly typed
term arguments and which proof terms cannot refer to as term variables. The
four generated bodies contain:

- no `_` placeholders;
- no inaccessible binder names;
- no tactic scripts; and
- no private helper references.

All three rewritten modules compiled. The named body sizes, in the original
theorem order listed above, were 1,887, 5,797, 50,113, and 7,172,142 UTF-8
bytes. On the initial test machine, the two smaller modules each compiled in
about 2.8 seconds. The module containing both `DualNumber` examples compiled in
about 44 seconds with heartbeat limits disabled; the reported maximum resident
set size was approximately 3.2 GB.

This resolves the binder-naming question: allowing names for existing binders
is sufficient to produce closed, directly compilable proof bodies for all four
examples. It does not resolve the size problem. Printing derived type-class
dictionaries explicitly makes the stress case exceed 7 MB, so a useful next
experiment should investigate compact sharing or another representation that
does not re-run type-class inference and does not duplicate those dictionaries.

### Sharing repeated subterms with `let`

The next pass introduces `let` bindings for repeated subterms before printing
the proof body. It operates on Lean expressions rather than rendered strings,
so it only replaces structurally identical terms and cannot split tokens or
cross a binding scope incorrectly.

The pass constructs the expression DAG and counts incoming references to each
structurally distinct node. It considers repeated application terms that do not
depend on a nested binder and whose expanded syntax tree contains at least 12
nodes. Candidates are introduced from smallest to largest, allowing a larger
shared value to refer to shared children. A limit of 512 candidates prevents
pathological output; none of these examples reached it.

The resulting measurements were:

| Theorem | `let`s | Unshared bytes | Shared bytes |
| --- | ---: | ---: | ---: |
| `Nat.count_le_setENCard` | 3 | 1,887 | 1,421 |
| `GenContFract.first_num_eq` | 6 | 5,797 | 1,102 |
| `DualNumber.commute_eps_left` | 32 | 50,113 | 4,923 |
| `DualNumber.range_lift` | 104 | 7,172,142 | 17,536 |

All three rewritten modules still compiled, and the generated bodies still
contain no `_` placeholders, inaccessible names, tactic scripts, or private
helper references. The two small modules compiled in approximately 3.2 and 2.8
seconds. The `DualNumber` module compiled in approximately 4.0 seconds with a
reported maximum resident set size of 0.92 GB, down from approximately 44
seconds and 3.2 GB for the unshared body.

This demonstrates that most of the apparent type-class dictionary explosion in
the stress case is repeated syntax, not irreducibly distinct proof content.
Explicit elaboration choices and compact output are compatible when repeated
subterms may be named with `let`.
